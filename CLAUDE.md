# Blackjack Trainer — notes for any Claude session working on this repo

## Keep every chat in sync

This repo's `main` branch is the single source of truth. GitHub Pages serves it directly.

1. **Before changing anything**, fetch the latest `main` and start from those files. Never start from a copy saved earlier in a chat.
2. **After changing anything**, commit and push to `main` in the same turn, then tell Nick what was pushed.
3. If `main` moved while you were working, rebase onto it and re-check your change before pushing. Do not overwrite someone else's newer files.
4. Only touch the files your change needs. Do not regenerate or replace icons, `manifest.json` or `sw.js` unless that is the task.
5. When anything in `index.html` or the cached files changes in a way users must pick up, bump `CACHE` in `sw.js`.

## Source and build

`index.html` is a generated file: the whole app (React + CSS + fonts) compiled into one offline page. **Never edit it by hand** — the next build overwrites it. Edit the source and rebuild:

- `src/app.jsx` — the entire app (all components, styles in the `css` template string, strategy/sim data)
- `src/head.html` — everything in `<head>` before the app styles (meta tags, icon links, inlined fonts)
- `src/entry.jsx` — mounts the app and the `window.storage` wrapper around localStorage
- `src/casinos.jsx`, `src/casino-map.js`, `src/casino-data.js` — the Casinos page, its map maths and its generated data (see "Casinos page" below)
- `src/input.css` — Tailwind entry
- `src/sound.js`, `src/sound-data.js` — the sound effects and their recordings (see "Sound" below; `sound-data.js` is generated)
- `src/planner.jsx` — the Plan tab and the casino scores (see "Plan tab" below)
- `src/phone.jsx` — the phone layout's own pieces: the Train and More menus, the session timer, Home's casino-trip card and the phone-only CSS (see "The phone layout" below)
- `src/smooth.js` — paints the dark themes' three soft gradients a pixel at a time, with dither, so Safari can't band them (see "Smooth gradients" under Liquid glass)
- `src/cover.js`, `src/coverdata.js`, `src/sim.js` — what a count play is worth and the card simulator behind it; `calFor` uses them for the "Deviations off" switch
- `build.sh` — `npm ci` once, then `./build.sh` writes `index.html` (scratch files go to `.build/`, ignored)

Commit the source change and the rebuilt `index.html` together. `build.sh` never touches the icons, `manifest.json` or `sw.js`.

## Navigation and motion

- Phone: bottom tab bar (see "The phone layout" above); desktop (1024px+): sidebar. On a computer Train is one row of tabs (see "Organized" below). On Train and Live play the table comes first and stats sit below it.
- **Keep pages plain** (Nick asks for simple, clean and sleek every time): the page header is the page name, the rules pill and, on a phone, the gear — no label above the name except today's date on Home and the link back to a menu on a phone. Explanations that aren't needed to use a page fold away behind `Info` ("How it works", "How to set it up", "About these numbers"), and secondary figures behind a "More …" link (Sessions shows four stats, with streak, average win/loss, upswing and swings behind "More stats"). Fold things away rather than delete them — every function stays.
- The compact top bar (`TopBar`) appears on scroll and shows only the page title and rules pill. Section chips in it were tried and removed at Nick's request (he wants the app kept clean) — don't add extra navigation rows. The "Ramp ↓ · Your numbers ↓ …" jump pills at the top of Bet spread were removed for the same reason.
- Desktop layout (1180px+): **one gutter** — the space under a card equals the space between the columns (20px; the block "Tightened" in the `css` string, which also balances headings' line breaks and keeps a paragraph from ending on one lone word). Every page is up to 1120px wide and uses two columns through `.dgrid` / `.dcol` wrappers, which are `display: contents` below that width — so the phone order is simply the source order. `.dgrid.wl` is a wide-left split (table or main content left, stats and reference right); `.narrow` and `.segw` keep single cards and switches from stretching. `.deskonly` / `.notdesk` show or hide an element on wide screens.
- Jump-to palette (`CommandPalette`, opened with ⌘K / Ctrl K, `/`, or the sidebar button): lists every page, drill and action — no theme rows (Nick removed those). When adding a page or drill, add it to `cmdItems` in `App`.
- `go(tab, options)` also fires a `bj-nav` event when the target page is already open; pages read it with `useNav` (train mode/view, drill, log sheet).
- `Seg` (segmented control) has a pill that slides to the selected option when its options sit in one row. In the dark themes the selected option is an accent-tinted glass pill with light text (the same look as the sidebar highlight), not the old ivory pill; the light theme keeps its solid pill.
- Keep motion small and purposeful, and add anything new to the `prefers-reduced-motion` rule.
- **One curve: it starts fast and finishes slowly** (Nick, four messages running: "all animations quicker with more easy ease"; "i only want an easy ease out, when all the animations start it should be fast"; "make the ease at the end more dramatic, a slow smooth finish"). Every animation and transition in the app runs on `--ez` = `cubic-bezier(.05,.7,.1,1)`: an **ease-out only, with a long tail**. It sets off at full speed, is half way there in the first sixteenth of its time and four fifths of the way in the first fifth, then spends the rest gliding to a stop. **Nothing eases in** — an ease-in-out (the first attempt at "easy ease") made everything feel slow to start and he rejected it at once; a plain, shorter ease-out (the second) started right but stopped too abruptly. `--ease`, `--fluid`, `--eo` and `--ee` are that same curve under their old names, so old rules follow along; motion driven from script uses the same curve through `ezOut(p)` (`useTween` / `Glide`), and `ezOutMap` (the map zoom in `casinos.jsx`). **A selection that travels is the one exception** — the tab bar's glass, a segment's thumb and the sidebar's highlight run on `--ez-slide` = `cubic-bezier(.22,.68,.1,1)`: `--ez` covers a third of the distance in its first frame, which is fine for something that grows or fades where it stands but made the tab highlight jump across the bar (Nick: "on mobile switching sections the highlight kinda glitches"). `--ez-slide` sets off just as promptly, never moves more than about half the highlight's own width in a frame, and has the same long finish. Don't put a sliding selection back on `--ez`. Don't reintroduce an ease-in, an ease-in-out, an overshoot or a bare `ease`. **Durations are for the finish, not the start**: things that move (presses, sheets, pills, bars, the palette, a switch) take .3–.41s, a tab's glass .46s and the page behind it .48s, charts about half a second, number glides 600 ms — the fast part of each is over in under a tenth of a second and the rest is the slow glide he asked for, so don't shorten them to "make it quicker" (that only cuts the finish off). Colour and hover changes stay at .16s. The splash is gone after 1.48 s. The sheet's exit is 220 ms (`Sheet` unmounts on that timer). The one thing with its own speed control is the card deal (below).
- **Entrance motion is one small kit** (in the `css` string, after `.growy`), so every chart and meter moves the same way. Use these rather than inventing new keyframes; all of them are switched off together in the `prefers-reduced-motion` rule, and all use `backwards` fill so nothing is left clipped or dashed once they finish:
  - `.drawline` + `pathLength="1"` on a solid SVG line: it traces itself on the app's ease-out (`--ee`). Used on the Sessions chart, the full-screen chart, the Home sparkline and the bell curve.
  - `.wipex` on the `<svg>` itself: a left-to-right reveal, for charts drawn with `vector-effect: non-scaling-stroke` or a filled area (Live play money chart, desktop Home chart), where a dash trace is unreliable.
  - `.fadein` (bands, dashed lines, labels) and `.popin` (the end dot). Add `.late` to anything that should land as the line arrives: it is timed off `--trace`, the one variable that sets how long a line takes to draw (0.6 s, most of it the slow finish; change the pace there, not per chart).
  - `.bary` on a column and `.barlab` on the number above it (set `--i` to the column's index for the stagger): bet ramps, the optimizer's bars, dealer outcomes. `.barx` on a meter fill: mastery, skills, long run, odds.
  - Wrap a chart's moving parts in a `<g key=…>` built from what is drawn, so a new filter or new data plays the entrance again (see `PnlChart`).
- **Arriving: everything comes in out of a soft blur, one after another** (Nick, asked how the motion should get smoother: cards arriving in turn, softer sheets and pop-ups, and "you can smooth by adding directional blur and maybe lowering opacity at beginning of animation"; the block "Arriving" near the end of the `css` string). How it is built, so it isn't undone:
  - **Two animations on one element.** The travel (`arrmove`: 18px up and a hair of scale, 14px on a phone) runs on `--ez`. The fade and the blur (`arrfade`: from invisible and `blur(7px)`, 5px on a phone) run on **`--ez-soft`** = `cubic-bezier(.22,.61,.36,1)`, a gentler ease-out. On `--ez` a fade is half over in its first frame, so the blur could never be seen; `--ez-soft` is for **what fades or sharpens only** — anything that moves stays on `--ez`. Neither eases in.
  - **Who arrives**: every direct child of a column (`.dcol>*` — cards, switches, the Home tiles), a page's own top sections, and the children of a phone menu (`.inturn`, on `TrainHub` and `MoreHub`). The page wrapper (`.shell>.rise`) only fades (`pagein`), so nothing is blurred twice.
  - **In turn only while a page opens.** `App` puts `data-enter` on the shell for 1.5 s when the page changes (`markEnter`, in the same layout effect that scrolls to the top; 2.6 s at launch) and the stagger (`--ai` × 48 ms from `nth-child`, the right column half a step behind through `--ac`) only applies under it. So a card that turns up later (the math after an answer, a saved list) comes straight in with no wait. Taking the attribute off changes a delay, not an animation's name, so nothing plays twice.
  - **Don't toggle an `animation` on something that arrives**: when the class comes off, the entrance plays again. The trainer's card shakes on a wrong answer, so it sits in a plain wrapper `div` and the wrapper is what arrives (before this, the old rise replayed after every wrong answer).
  - **Small things that appear in place** (`.rise`: an answer, a note, unfolded `Info` text; `.resin` on the phone) rise 9px out of `blur(4px)` on `--ez-soft`. A whole grid or a felt keeps the plain version (`riseplain`).
  - **Sheets, the rules dialog and the palette**: the glass panel glides up and fades (`panelup` / `panelpop` with `panelfade`), and **what is on it** comes into focus a beat behind (`focusin`, `blur(9px)`, on the title row and the body). The blur is never put on the panel itself: the panel already blurs the page behind it, and a filter on top of that could not be checked in Safari. Scrims fade over .36s; a sheet leaves in 220 ms (`paneldown`).
  - **A dealt card** is `blur(3px)` as it sets off and sharp as it lands (in the `deal` keyframes, beside its brightness).
  - **The blur is the ordinary `blur()` filter riding the movement**, which both Chrome and Safari animate on the graphics card. **A blur in one direction only was not used**: CSS has none, and the SVG filter that can do it is drawn slowly by Safari, on the iPhone most of all. To cut the cost, cards past the seventh in a column, and the second column on a phone, arrive with no blur (`--arr-blur:0px`). If it ever stutters on Nick's phone, lower `--arr-blur` (0px switches it off everywhere) before anything else. All of it is in the `prefers-reduced-motion` rule.
- **Folds glide; nothing opens or closes in one frame** (Nick: "restyle making everything sleeker and smoother more improved animations. check everything"; the block "Second pass" near the end of the `css` string). Two pieces in `src/app.jsx`, exported for the other files:
  - `<Fold open>` — a block that exists only while open (every `Info`, the session sheet's "More details", the casino sheet's "More rules", a casino's full report). Opening grows it from 0 to its height while its contents come into focus (`.foldin`: 6px down out of `blur(4px)` on `--ez-soft`); closing shrinks and fades it, then unmounts it. **Use it instead of `{open && <div className="rise">…</div>}`** for anything that pushes the page down. Put spacing inside it (`pt-…` on the Fold, not `mt-…` outside) — `.fold` is `display: flow-root`, so margins inside are part of what animates.
  - `useGlideH(dep)` — put its ref on a list that grows or shrinks when `dep` changes ("All N casinos", "N more", "More tables", Sessions' "Show all" and "More stats", "All N plays"); its height glides from the old size to the new. Wrap the rows in one `div` for it if they have none (sibling rules such as `.prow+.prow` still hold).
  - Both animate `height` through the Web Animations API on **`--ez-slide`** (`FOLD_EASE`) — a changing height is something that travels, and `--ez` would move a third of the way in the first frame — 480 ms open, 340–360 ms closed; both read `offsetHeight` (layout, not transforms, so an arriving card's scale doesn't skew them), pick up mid-move from wherever the height is, and leave no inline height or overflow behind. Both are off under reduced motion. Content folds are the one place a height animates; chrome (bars, pills, the sidebar) still only moves with `transform`.
- **Every transition names its curve.** The last bare ones (a duration with no timing function, which the browser runs as `ease`) were given `var(--ez)` — about 55 across the four CSS strings and inline styles. Write new ones with a curve.
- **The primary button is quieter**: a smaller glow (`0 6px 16px -9px` at .42), a little more on hover on a computer, and a press that dips to .975 so a tap is felt (.99 couldn't be seen).
- **A theme change crossfades** where the browser has view transitions (Chrome, Safari 18): `ThemePicker`'s `pick` runs `setT` inside `flushSync` within `document.startViewTransition`, and the old look dissolves into the new over .46s. Elsewhere it switches as before. The page glow (`src/smooth.js`) fades out at the change and back in once repainted.
- **A money figure never breaks after its minus sign**: `money`, `sgnMoney` and `shortMoney` put a word joiner (U+2060) after "−", and the few places that write "−" before `money(…)` themselves use "−\u2060" too ("1 in 10: −" / "$1,225" used to split across two lines on a phone). The CSV export uses raw numbers and is unaffected.
- Numbers that move: `<Glide v={n} f={format} />` glides to a new value when it changes (add `enter` to also count up from zero when the page opens — headline numbers only). It is a tiny component on purpose: only its own text re-renders each frame, never the page. `useTween` is the hook underneath (used by `LuckGauge`, whose marker rides the curve). Don't tween a number with a hook at the top of a big page component.
- Small phones (320–370px) are checked: the tab capsule's six tabs share the width (`.navbtn{flex:1 1 0;min-width:0}`, labels step down a size), the page title and rules pill shrink so they never touch, and rows of answer buttons carry the `acts` class (side padding, no wrapping). On touch screens small text links, steppers and round icon buttons get a larger invisible touch area (`@media (pointer:coarse)` in the `css` string) — keep new small controls inside those selectors.

- Rows that must fit a phone are checked at 320, 360, 375 and 390px, not just one size: a row of five answer buttons tightens below 390px (the `nth-last-child(n+5)` rule next to `.acts`), the bet table on Bet spread is `.btrow` (below 431px "Show frequencies" swaps the EV/round column for Freq % instead of adding a sixth column), the deviation list is `.devrow`, and the Fill chart play picker is `.chipseg.brushes`. - Sessions → Export CSV saves a file on a computer; on a phone it shares a real `.csv` file when the phone allows it, then falls back to sharing text, then to the clipboard.
- **Nothing slow may run while a page opens or on a keystroke.** The drawdown replay (up to three million rounds) and the Plan tab's bankroll paths go through `useDeferred(key, fn, keep)`: it waits until the page has finished animating in (about 1.1 s after it opens, so the sum never makes a chart trace stutter), debounces itself while you type, and remembers answers by key. Its results are `undefined`/`null` until ready, so the UI must cope ("…"). **Hand it a generator and it works a few milliseconds at a time**, so taps and scrolling stay live while the sum runs: `drawdownSteps` and `growthSteps` yield as they go, and `drawdownFromMix` / `growthSim` run the same steps straight through (same paths, same answer) for the checks and for anything that needs the number at once. Before this the Sessions page froze for most of a second on a phone, a moment after it opened. Use the same pattern for any new heavy sum.
- **Hover, press and focus are one kit** ("hover, press and focus: one kit" in the `css` string; Nick asked for everything clickable to react, and to react the same way). Hover applies only where there is a pointer. A safety-net rule gives any button or link without a look of its own a slight shift, lighter on dark themes and darker on light ones (`--hov`); it carries almost no specificity, so a control's own hover rule wins. On top of it: text links shift further (`--hov-t`) and dim when pressed — give a new text link the class `lnk` (underlined buttons are covered already); a full-width row (a switch row, a Settings row, a fold-away heading) takes `rowh` for the faint wash list rows have; a card that is one big button takes `cardbtn` and its hairline rim turns the accent colour (cards have no border any more, so `border-color` does nothing on them); Home's shortcut tiles are `.qa`; the seats on Bet spread are `.seat`. ## Sound

The table sounds are **real recordings**: a card dealt, a chip bet and the shuffle come from Kenney's "Casino Audio" pack (CC0 — `tools/sounds/kenney/License.txt`). Nick rejected two rounds of synthesized card and chip sounds as fake, harsh and too many, so don't go back to synthesizing them.

- `tools/sounds/kenney/` holds the chosen `.ogg` files; `tools/sounds/build-sounds.py` (needs numpy and an ffmpeg with the `rubberband` filter) prepares each one and writes `src/sound-data.js` — **generated, don't edit by hand** — as small MP3 clips in base64 (about 45 KB), so the app stays one offline page. To use different recordings, edit `CLIPS` in that script, run it, then `./build.sh`. The rest of the pack (card fans, shoves, chip handling, dice) is not in the repo; ask Nick for the zip again or get it from kenney.nl.
- **Never trim a recording short to make it fit — speed it up at the same pitch instead** (Nick's instruction, after hearing clips cut down to just the snap). The quiet slide before a card lands is most of what makes it sound like a deal, so the script keeps the whole sound and only cuts real silence from the ends; a clip that is too long for the pace gets a `tempo` in `CLIPS` (cards 1.3–1.5, the full seven-stroke shuffle 1.55 so it fits the "Shuffling" pause). Each stretch is tried three ways (ffmpeg `atempo` and two `rubberband` settings) and the one that changes the recording's tone and snap least is kept. Card clips come out 170–260 ms, longer than the gap between dealt cards, so a deal overlaps into one run instead of separate clicks. A second set, `cardq`, is the same five recordings quicker again at the same pitch (`QUICK` in the script, 105–160 ms) for fast dealing.
- `src/sound.js` decodes the clips on the first tap and plays them (skipping only the dead silence an MP3 decoder leaves at the front — not the slide). `sfx(name, delayMs)`: `card` (one of five slides, never the same twice running), `chip` (one of four), `shuffle`. Recordings play dry at the levels in `TRIM`; cards are the most frequent so they sit lowest.
- **Keep it sparse** (Nick: "too many sounds"). The default set is those three. The answer and result notes — `right`, `wrong`, `win`, `blackjack`, `lose`, `pass`, soft synthesized wooden notes — are the `feedback` group, **off by default** and opt-in from Settings. No sounds on ordinary taps, tabs or sheets.
- **Cards:** `PlayingCard` plays `card` when it mounts, so anything that deals a card is heard without extra code; a face-down card is a plain div, so put `<Flick d={ms} fly={seconds} />` beside it. **The sound keeps time with the card at any dealing speed:** the card passes its flight time (`fly`, default `DEAL_FLY`) as `sfx("card", delay, { fly })`, and `card()` in `sound.js` places the recording so its snap (each clip's loudest 5 ms, measured when it is decoded) falls where the card lands — `LAND` (0.5) of the way through its flight, which is where a card on the app's ease-out has covered 95% of the distance — not where it sets off. A flight under 0.2 s uses the `cardq` set. Cards that would land together are heard one after another, 35–90 ms apart depending on the flight. If the deal's curve or `LAND` changes, re-run the offline check below with a few `fly` values and compare snap times with landing times (they should agree within about 15 ms).
- **Notes (when switched on):** `logResult` is the one place every drill and test answer passes through, and it plays `right` or `wrong` (pass `quiet` as the fourth argument when one answer logs twice, as the count drill does). Live play is skipped there: it plays `wrong` when a mistake is flagged and `win` / `blackjack` / `lose` once the round is settled. Passing a test plays `pass`. Live play also plays `chip` on a bet and `shuffle` on a new shoe (table group).
- **The settings** (`soundPrefs()` / `setSoundPrefs(patch)`): on/off, volume, `table` and `feedback`; each sound's group is in `GROUP`. Saved on this device only under `bj-sound-v1` (not in `BACKUP_KEYS`); the stored setting carries `v`, and one saved before `v: 2` has the notes switched off once. The full set is the Sound card in Settings (`SoundCard`); the Live play table settings carry just the on/off switch (`SoundToggle`). Both stay in step through the `bj-sound` event, and changing a setting plays a sample.
- Nothing plays before the first tap or key press (browsers require it), while the page is hidden, or with the switch off; a phone's silent switch mutes it too.
- To check a change without ears: bundle `src/sound.js` alone, swap `AudioContext` for an `OfflineAudioContext`, `await soundReady()`, render, and read the peak level (cards about 0.25, chips and shuffle about 0.35). That checks levels, not whether it sounds good — only Nick's ears can, so send him a rendered preview after changing a sound.

## Live play

Settings open as a sheet from the gear on the table header (`setupOpen` in `Play`) and persist to `PLAY_KEY` (`_playPrefs`): hand totals, running count, auto-deal the next hand (skips the Next tap, the bet is still the user's), count check every 3/5/10/20 hands or off, dealing speed (a 9-stop slider, `DEAL_SPEEDS`: Blitz 0.25 … Normal 1 … Very slow 3, a twelve-fold range; a saved value that is no longer a stop snaps to the nearest), and New session. `speed` multiplies every deal timing through `ms()` — the stagger, the dealer's draws, the sit-out hand — and `dealFly(speed)` is how long a card is in the air (0.35 s × speed, never under 0.12 s), which is also what times its sound. The pause before auto-dealing follows the speed too (`autoMs`: 1.5 s × speed held between 0.45 and 4.5 s, so every stop has its own pause — the old 2.8 s ceiling made the three slowest wait the same; after a mistake 3.2 s × speed held between 1.8 and 6 s so the message can be read). **With auto-deal on, the Next hand button is replaced by a bar that fills over that pause** (`AutoNext`, Nick: "if the user selects to deal hands automatically, remove the next button and show a progress bar until the next hand is dealt"): the same capsule size as the button, filling from the left at a constant rate (`autofill`, linear because it is a clock, not a movement), tinted red after a mistake, and a tap on it deals at once (Enter and Space still do). Train's Practice uses the same bar for its own automatic deal (1.4 s after a right answer, 3.4 s after a wrong one; it has no speed setting) in place of the old strip across the top of the answer; opening the odds stops the clock and brings the button back. the opening deal staggers through `HandView`'s `stagger` / `base` / `dur` props so cards land one at a time.

Page order: the table card (felt, then the bankroll/net strip, then the controls), `SpreadMini`, `ShoePanel` (wide screens only), the record card, the percentile card, mistakes. On wide screens the by-count table and the mistakes sit under the table in the left column instead (see "More for wide screens"). `SpreadMini` is the ramp; the current true count is lit and named only while "Show the running count" is on — with the count hidden it is a plain reference so it can't give the count away. `ShoePanel` is the shoe at a glance: a penetration bar with a tick per deck and the cut card in red, cards seen and cards left, and — only while the count is showing, for the same reason — the true count's path through this shoe. Its line comes from `trace` in `Play`, one sample per ~1% of the shoe, emptied when a new shoe starts; the vertical scale grows to fit the shoe's own peak. The record card holds a `scope` switch (this session / all time), the stat row and the money chart; the percentile is built from `evHour`/`sdHour`/`rph`. Both charts show on phones too. On wide screens the table is the left column and everything after it the right.

All-time hands, money, clean rate, count checks and a per-hand money list live in `PLAYALL_KEY`, which is in `BACKUP_KEYS` so it syncs: the counter names are in `SYNC_COUNTERS` so two devices' totals add up, and the money list is `{id, n}` per hand so their hands merge; `syncTidy` sorts and thins it (`thinPts` adds neighbouring hands together past 600 points). It saves every tenth hand and on pagehide/visibilitychange, never once per hand, and reloads itself on `bj-sync-applied`. Wipe it from Settings → Reset skill results.

Keyboard shortcuts for the table are changeable in that same sheet, on a computer only (`.kbdonly`, same media rule as `.kbdhint`): `KeyBinder` edits `keys` (defaults in `PLAY_KEYS_DEF`, saved with the other prefs in `PLAY_KEY`). Keys live at the same moment must differ (`PLAY_KEY_GROUPS`), so taking another action's key swaps the two. Enter and Space always deal the next hand. The key hints under the table read from `keys`, and the table ignores keys while the settings sheet is open.

## Count plays that go by the running count (0+ and 0−)

The app rounds true counts toward zero, so a true count of 0 covers running counts on both sides of zero. The plays the BJA charts print as "0+" (16 vs 10) and "0−" (12 vs 4, 15 vs 10 with surrender, and A,8 vs 6 in H17), plus A,7 vs 2 in H17 (0−, measured by the app's simulator — the BJA chart prints no index for it), turn on the **sign of the running count** instead: 0+ makes the play on any positive running count, 0− drops the basic play on any negative one, and a running count of exactly zero is basic strategy. They carry `edge: "+"` or `"-"` in `DEV_TABLE`; `devOver(d, tc, rc)` is the one place that decides whether a deviation's "above" play applies — use it, never `tc >= d.idx`. `correctPlay` takes the running count as `opts.rc` (Live play passes the shoe's); without it a true count of 0 is read as a running count of 0. `idxLabel(d)` prints "0+" / "0−", and drills show the running count's sign beside a true count of 0 (`devDrillCount`, `rcs`). 13 vs 2 (−1 on the chart: hit at −1 and below) is an ordinary index, stored as 0 and shown as −1 (see `chartIdx` below).

## Deviations on or off

Game rules → Advanced → **Deviations** (`rules.devs`, on unless it is exactly `false`; read it through `devsOn(R)`, since
rules saved before the switch existed have no such field). Off means basic strategy on every hand: no count plays and
no insurance.

- **Calculator:** `calFor(R, seats)` is the one door. With deviations off it builds the no-insurance table (`calBase`,
  the old `calFor` body) and takes every count play off through `coverCal(…, { skip_all_deviations: true })` from
  `src/cover.js`, then marks the result `basicOnly`. Checked against six games played out with basic strategy only
  (300 million rounds each): within about 2%. `coverCal` ignores deviation and insurance cover for rules that already
  have deviations off, so they can't be taken off twice.
- **Play:** `correctPlay` skips the count plays unless `opts.devs` is passed. Live play grades on basic strategy and never wants insurance. `src/sim.js` deals the same way.
- **Left alone on purpose:** the deviation list, drills and tests in Train stay available so they can still be practised.
- The setting travels with the rules: it is in each session's saved game (the session editor has the same switch), in
  `rulesLabel`, and at the end of the rules pill as "no dev". The pill now shortens with "…" instead of running under
  the page title (`.rulespill .mono`), which also fixed long rule sets on small phones.

## Where the calculator's numbers come from

`CALR` / `CALQ` / `CALD` / `CALX` at the top of `src/app.jsx` are measured tables, packed by `tools/sim/build_cal.py` from
the simulator in `tools/sim/table_sim.c` (64 billion rounds in all; the README there lists what each part is and how to
re-run it). Don't edit those lines by hand. Three things must say the same thing whenever a play or an index changes:
`DEV_TABLE` in `src/app.jsx`, `DEV_DEFS` in `src/sim.js`, and `defs[]` in `tools/sim/table_sim.c` (same order — the
position is the play's id in the cover data). `CAL_ROUNDS` and the Settings paragraph state the round counts; keep them
true if tables are re-run.

The simulator's `audit` mode checked every basic strategy cell and every count play in all 20 games (5 deck counts ×
H17/S17 × surrender). With 4, 6 and 8 decks every cell and index holds. **How negative chart numbers are stored and shown.** A play's index in `DEV_TABLE` (`s17` / `h17`) is always the lowest
true count at which its "above" play is made. The BJA chart prints the plays where basic strategy is already the above
play the other way round — "−1" on 13 vs 2, on surrender 16 vs 9 and on surrender 15 vs A (H17) means *hit at −1 and
below* — so those are stored as 0 and **shown as −1**: `devLow(d)` marks them, `chartIdx(d)` is the number the chart
prints (one below the stored index) and `idxLabel`, the deviation list, the fill-in test, the drill explanations and the
cover catalog all show that number. `devPlay(d)` is the count play itself (the one that
isn't basic strategy). Never show a raw stored index to the user. Surrender 16 vs 9 and 15 vs A (H17) used to be stored
as −1 (hitting only from −2); the check measured surrendering 16 vs 9 at −1 as about 1% of the bet worse than hitting,
and Nick confirmed the chart. The shipped tables and cover-play costs were dealt with the old indices; the difference
is under 0.005% of a bet at a true count of −1, far inside their noise, so they were not re-run. With 1 and 2 decks several plays differ from the shoe
charts (doubling 9 vs 2, splitting 6s vs 7 and so on) — expected, BJA's charts are for shoes, and the app deliberately
uses one chart for every deck count. Soft 18 vs 2 in H17 ("0−": stand on a negative running count) came from that
check; the BJA chart has no index there.

## Sessions

The Luck check card's **Long run** bar measures N₀ from the log itself, not from the spread currently set in the app:
`sessionStats` returns `expHour` and `modelSd` (each session's own snapshot edge and swing, weighted by its hours),
and N₀ in hours is `(modelSd / expHour)²`. It follows the page's period and casino filters, like every other figure on
the card. With nothing logged, or when the logged average has no edge, it falls back to the current spread's `n0` and
the caption says which one it used.

## Checking the arithmetic

`tools/checks/run.sh` builds the app with a few internal functions exported and runs `tools/checks/math-test.jsx` in Node (its random walks are seeded, and count dips between steps exactly, so a run always gives the same answer — they used to fail about one run in three on sampling noise alone; `SEED=n` tries another seed), then `tools/checks/plan-test.jsx` for the Plan tab (see "Plan tab"). The first covers: payouts (`settle`), hand values, the normal curve (`PhiN`), the chance of a dip (`pDip`, against a brute-force random walk), the calculator's formulas (EV, swing, risk of ruin against a simulated walk, N0, session bankroll) across deck counts and table sizes, and about 70 basic-strategy and count-play spot checks against the published charts. It prints "all N checks passed" or each failure; run it after touching any of those. It does not re-measure the edge tables — that is the simulator's job (above). Two things it found that are by design, not bugs: heads-up with a $0 bet at the starting count never plays a hand (nobody else moves the count), and 12 v 5, 12 v 6 and 13 v 3 have no count play because BJA's chart leaves them out.

## Checking for bugs

- `tools/checks/lint.sh` reads the source for names used but never defined, hooks out of order, duplicate keys and similar. Run it before pushing: a rename that misses one use doesn't fail the build, it fails when that line runs. That is how "Count down a deck" came to blank the whole app (`deckCards` and `dealKey` no longer existed) and how Home stopped showing passed tests (`TEST_KEY` for `TESTS_KEY`, hidden by a `try`). It prints "no problems" when clean.
- `src/entry.jsx` does two things before the app draws. **Repair**: `bj-sessions-v1` and `bj-log-v1` must be lists of records — anything else (a wrong file pasted into Restore, a half-written sync) is set aside under `__bad-<key>` rather than deleted, entries that aren't records are dropped, and a session's hours and result are made numbers. Before this, such data blanked the app on every start with no way back. Every other saved key already survived being the wrong shape; if a new list is added to storage, add it to `repair`. **Safety**: an error boundary round `App` — if a page still fails to draw it shows "Something went wrong" with Reload and "Copy a backup of my data" instead of a blank screen.
- A brief sideways overflow while a card flies in from the shoe is expected and can't be scrolled to (`html{overflow-x:hidden}`).
- **Saved data is read defensively at the three places that used to blank a page**: the count drill's totals (`bj-count-v1`: only a record of numbers is taken), test results (`testsOf`, a record of records) and the game rules (`cleanRules`: a deck count or penetration the app doesn't offer falls back to the default; saved rules that aren't a record open the first-run dialog). Restore refuses a paste that holds none of the app's keys, and writes a value that isn't text as JSON. `tools/checks`-style proof lives outside the repo: every saved key was loaded with eleven wrong shapes and every page opened (198 combinations, wide screen).
- **A shoe can run out.** The count drill never deals more than the shoe holds: `amount` in `Counter` is what was picked (`want`) capped at the cards a fresh shoe can deal (one is burned), with a one-line note under the picker when it is capped — 52 cards from one deck used to stop dead at 51 with an error, and that is the default with a one-deck game. In Live play `draw()` shuffles a fresh pack when the last card has gone (one or two decks cut deep: a round started on card 46 of 52 can need a seventh card), finishes the round from it with the count carried on, and marks the shoe `spent` so the next bet starts a proper new shoe with the usual "Shuffle." message. `src/sim.js` already did the same.
- **Tests must not give the answer away or mark the count play wrong.** The true-count buttons are nine in a row with the right one at a random place (`off`, as in the drill) — in the 20-conversion test it was always the middle button. The 100-hand test takes its plain hands from `plainDeck(rules)`, which leaves out every hand that has a count play (those are only asked as count plays, as in Train's mixed mode): a plain hand is shown with a count from −2 to +2 and marked against basic strategy, so 16 v 10 at +1 used to want "hit". About two tests in three held such a hand, and the test needs 100 out of 100. `tools/checks/math-test.jsx` now checks that no hand `plainDeck` returns has a count play in that range, for 24 rule sets.

## Liquid glass (after iOS 26)

Nick asked for an Apple-style liquid glass look, then for it to go further, "like iOS 26". It is one block at the end of the `css` string in `src/app.jsx` ("Liquid glass, after iOS 26"), driven by four variables: `--gl-edge` (the specular rim: a gradient brightest at the top-left and bottom-right corners), `--gl-hi` (the bright top edge on small controls), `--gl-rim` and `--gl-sheen` (a soft sheen from the top-left corner); the blur itself is written out where it is used. Light themes re-point them.

- **Measured against Apple's own description** (Nick: "study Apple's liquid glass and improve ours"; the block "The material, refined against how Apple describes Liquid Glass" near the end of the `css` string). Apple's material is clear, reflects and refracts what is around it, takes its colour from the content behind, answers movement with specular highlights, and is a layer of controls floating over content rather than the content. So: (1) content cards have a softer rim (`--gl-edge-soft`) than the controls; (2) the small floating pieces blur less (18–20px) and saturate more, so they read as clear, not frosted; (3) edges bend light — `--gl-lens` is the shared edge (bright rim, light gathered just inside, a little weight along the bottom) for pills, round buttons, ghost buttons, the tab capsule, sheets, the rules dialog and the palette, and `--gl-bead` is a selection (tab, sidebar, segment, chip): a tinted, slightly raised bead of the same glass; the primary button has a gloss band; (4) a pressed switch knob or slider handle turns into a clear lens. **Real refraction is not attempted**: it needs an SVG displacement filter inside `backdrop-filter`, which only Chromium supports, and Nick is on an iPhone. A scroll-linked tilt of the tab capsule rim (`--gl-tilt`) was tried and removed: it re-styled a blurred layer on every scroll frame, which could not be checked on an iPhone from here.
- **The tab bar is a floating capsule** (`.bottom-nav > div`): `.bottom-nav` itself is now only the fade the page disappears into, with `pointer-events: none`, so taps beside the capsule reach the page. The selected tab is a capsule over the whole button (`.navbtn.on`), not a lozenge round the icon. Checked at 320, 390 and tablet widths; below 350px the side padding tightens.
- **The top bar has no bottom line**: it is blurred glass with a plain gradient under it (`.topbar::after`, 20px) that the page fades into. Not a `mask-image` on the bar: a mask on a blurred layer can drop the blur in Safari.
- **Sheets float on a phone** (below 1024px): inset 8px from the screen edges, round all the way round; the wrapper's bottom padding stands in for the safe area, so the sheet's own content padding is cut to 22px there.
- **Sheets, the game-rules dialog and the Jump-to palette are the clearest glass in the app** (Nick twice sent a pop-up that "doesn't have it": a thin dark fill over a dark scrim reads as a solid box). So the scrim is light (`--scrim` .4 in the dark themes), the fill is thin (`color-mix` of the sheet colours at 58–72% with a light tint on top), the backdrop is blurred, saturated and brightened a little, and each has the rim. None of the three scrolls itself: `Sheet` is a flex column whose `.sheetbody` scrolls under a title that stays put, and the rules dialog has the same inner box. Keep it that way — a panel that scrolls takes its rim with it. Close buttons are `.xbtn`.
- **The rim** is a `::before` with a `--hair` padding and a mask (`.card:not(.rulesdlg)::before`, the tab capsule, the palette), which is why `.card` is `position: relative` through `:where()` (zero specificity, so a Tailwind position class still wins) and its own border is transparent in the dark themes. Don't put the rim on anything that scrolls its own content — the ring would scroll with it. And don't use `.card::before` or `.card::after` for anything else (`::after` is the pointer light).
- **Edges are built one way** (Nick sent a close-up of a card corner: "these edges are off" — the rim was a 1px grey band sitting inside a transparent border, hot at the corners, and pills had a border plus a second ring inside it). Now: (1) **one line, exactly on the outer edge** — glass surfaces have no CSS border at all (`.card`, `.sheet`, `.cmdk`: `border: 0`, the `::before` ring is the edge), and small controls (`.rulespill`, `.iconbtn`, `.stepbtn`, `.btn.ghost`, `.sn-search`, `.sn-rules`, `.xbtn`, `.gchip`) keep a transparent border for their size with the fill clipped to the padding box and the line drawn by `--gl-lens`; (2) **a hairline**: `--hair` is 1px on an ordinary screen and .5px at 2x and above — don't go thinner (.34px for 3x phones made the browser round the rim away); (3) **continuous**: `--gl-edge` / `--gl-edge-soft` run at 155deg and never fade to nothing along a side; (4) the light themes add a `0 0 0 var(--hair)` outer shadow in the text colour in place of the old border. **So a card can't be coloured with `borderColor`** — it has no border. Use a class that tints the rim: `.focuscard` / `.focusrim` (accent), `.rim-ok` / `.rim-bad` (a right or wrong answer in Train, 1px so it reads). Check edges with a 3x close-up, not a normal screenshot: a 1px problem is invisible at normal size and obvious on a phone.
- **One scale for shape, surface and depth** (Nick: "a full style upgrade ... sleek and clean and very silky smooth"; the block "One system for shape, surface and depth" near the end of the `css` string). **Shape**: three corner sizes and the capsule, nothing in between — `--r-s` 10px (key caps, the ×1 buttons), `--r-m` 14px (anything typed in or tapped inside a card: inputs, answer buttons, tiles), `--r-l` 22px (a card), capsule for buttons, chips and selections. The Tailwind corner classes are re-pointed to that scale inside `.bj` (`rounded-md` 9, `rounded-lg` 12, `rounded-xl` 14, `rounded-2xl` 18), so use them or the variables rather than a new number. **Surface**: answer buttons (`.opt`) and the Home shortcuts (`.qa`) are the same glass as every other small control (the `--gl-lens` edge, no grey border; an inline `border` on an `.opt` is overridden, so show a state with its background); cards are one flat tint in the dark themes; number boxes (`.in`) are lighter wells. **Depth**: a very faint wash of the theme colour at the top of the page (painted by `src/smooth.js` in the dark themes — see "Smooth gradients"). Numbers are tabular everywhere. On desktop the bet table's boxes are capped at 190px (`.btrow`).
- **Smooth gradients** (Nick sent a photo of his Mac — rings round the pointer light on a card, steps in the page's fade — and then, after a first fix, "gradients still look rough running in Safari"; the block "Smooth gradients" near the end of the `css` string, and `src/smooth.js`). A screen has 256 levels of each colour; a soft glow on a dark surface crosses only a few of them, and a browser that rounds each pixel to the nearest level draws it as flat bands with edges. **Chrome dithers its CSS gradients and hides this; Safari does not**, so a gradient that looks fine in Chrome can look stepped on Nick's Mac and iPhone. **Noise laid over the finished picture does not fix it** (that was the first try, a grain layer over the whole app, now removed): the bands are already drawn, and on a sharp screen fine noise averages out to the eye and leaves them — measured, it left the visible error unchanged, where dither added *before* the rounding cut it about five-fold. CSS can't dither, so in the dark themes: (1) **every large surface is one flat colour** — the page (`html` paints `--bg`; `body` and `.bjroot` paint nothing), cards (`rgba(var(--fg),.045)`, no sheen), sheets, the rules dialog, the palette, the splash — because a flat colour cannot band; (2) **the three soft gradients worth keeping are painted by `src/smooth.js`** with the dither in them: the page's glow (the theme's "velvet" lift and two faint washes of the accent) on `canvas.glowbg`, fixed behind the content at `z-index:-1`, one canvas pixel per screen pixel, written as solid colour (the page colour with the light added — a see-through pixel is stored multiplied by its opacity, which rounds most of its colour away and left faint streaks), starting at the sidebar's edge on desktop so the blurred sidebar sits on flat colour; the light under the pointer, a picture in `--plight` that `.card::after` positions (the listener in `App` keeps it on whole screen pixels so the dither isn't blurred away); and the table felt, a picture in `--feltimg` stretched over every `.felt`. They are painted in slices of a few milliseconds just after the app opens and again when the theme changes (`applyTheme` fires `bj-theme`) or the window's width does; until a picture is ready the CSS gradient stands in. **Don't put a slow, faint gradient on a big dark surface in CSS** — add it to `smooth.js` or make the surface flat. Small or steep gradients (a button, a bar, a capsule, the bars' fades) are fine: their bands are too narrow to see. Light themes keep their CSS gradients (a one-level step is far too small to see on a bright surface) and have no glow canvas. **To check without Safari**: Chrome does not dither canvases or pictures, so a Chrome screenshot of these three is what Safari shows; blur it a few pixels *in floating point* (blurring an 8-bit image re-makes the bands), multiply the contrast about 14×, and look for rings. That cannot check a CSS gradient — Chrome's own dither hides those — so reason about any that remain.
- **Real blur only on what floats over the page**: tab capsule, top bar, sidebar, the floating rules pill, sheets, the Jump-to palette and the sync toast. Cards get the rim but no `backdrop-filter` — nothing sits behind them, and dozens of blurred layers make a phone scroll badly. Don't add blur to cards or list rows.
- **Shapes**: cards are 22px round (16px when nested), `.btn` and the sliding segmented control (`.chipseg.slide`) are capsules. A `.chipseg` that can wrap to several rows keeps its 12px corners.
- Sheets and the palette are see-through through `color-mix()` inside an `@supports` rule, so older browsers keep the solid sheet. `prefers-reduced-transparency` turns the chrome solid again.
- Pills, round buttons and ghost buttons share one capsule: a top-to-bottom tint with the `--gl-hi` edge. Give a new small control the same two declarations rather than a flat fill (`.pchip` on the Plan page does).
- Shadows in the light rules use `rgba(var(--fg),…)` so Kiera and any later light theme tint them their own colour.
- **One selection look on phone and desktop**: the sidebar's sliding highlight (`.sn-glide`), the tab bar's (`.navglide`, placed from `--i` / `--n`), a segment's thumb and a selected filter chip (`.gchip.on` — `ChipRow`, the hour and casino picks in the session sheet) are all the same accent-tinted glass capsule; in the light themes the segment and the chip are the solid accent pill. The old white selected chip and the sidebar's left accent bar are gone. Use `.gchip` for any new chip instead of inline colours.
- **Switches, sliders and wells**: a switch's knob and a slider's handle are the same light bead of glass (a capsule a little wider than tall, bright top, soft shadow); the switch track, `.in` text boxes and segmented tracks are cut into the surface (a shadow along the top inside, a hairline of light along the bottom).
- A single-row `.chipseg` is a capsule; `Seg` adds `.rows` when its options wrap, and `.rows` and `.brushes` keep 12px corners. Inputs (`.in`) are 14px round; a desktop dialog is 30px, the palette 24px, the map's zoom buttons are round glass.
- **Fluid motion, kept quiet** (Nick: very subtle, then smoother and more fluid, then quicker, then fast off the mark): nothing bounces, and there is one curve — see "One curve: it starts fast and finishes slowly" under Navigation and motion for the curve and the durations. **`Glider`** (the tab bar's `.navglide` and a segment's `.thumb`) moves a selection as **one `transform` animation** through the Web Animations API: CSS only places the element (`transform: translateX` from `--i`, no transition), and `Glider` bakes the slide and the stretch into the same 33 keyframes, about one a frame, played linearly — a single compositor animation, which is the path every browser handles best. Position follows `--ez-slide` (`slideEase`); the stretch follows the highlight's speed (longer and a hair thinner while it is fast, 9% at most, its own size as it glides in) and is eased in over the first 60 ms so it never pops. A second tap mid-move reads where and how stretched it is from the computed matrix and carries on from there. `ms` is 480 for the tab bar and 400 for a segment; a segment passes `gap={4}` (the space between its options). **It used to be a CSS slide on `translate` plus a separate `scale` animation**; with the fast-start curve the glass covered a third of the bar and popped 13% wider in its first frame, which is what Nick saw glitch on his phone — don't split it into two mechanisms again, and check any change by sampling `getBoundingClientRect()` every frame after a tap (no frame should move the highlight more than about half its width, and its width should rise and fall smoothly). Don't animate `left` / `right` / `width`.
- **A tap answers on the next frame** (the "very silky smooth" pass; measured with a 4× slowed processor, a tap to the first frame went from up to 100 ms to about 15 ms). `App` keeps two tabs: `navTab` is what the tab bar and sidebar point at and moves at once; `tab` is the page that is showing and follows inside `startTransition`, so a heavy page (Bet spread, Sessions, Casinos) is drawn in slices behind the moving highlight instead of holding it still. `go()` is the only place that sets either; anything that marks the current place in the navigation reads `navTab`, anything that decides which page to draw reads `tab`. The scroll back to the top happens in a layout effect when the new page appears, not at the tap (the old page used to jump to its top first). `warmCasinos()` (in `src/casinos.jsx`) unpacks the casino list and the US map in three small pieces a few seconds after the app opens, so the first visit to Casinos is as quick as the rest.
- **Only `transform` and `opacity` move** on anything that animates while the page scrolls or a tab changes. The desktop rules pill used to animate `padding` and `font-size` on a blurred layer; it now glides with `translateY` on the rail and `scale` on the pill. Don't animate layout properties (`padding`, `top`, `width`, `font-size`) on chrome. Buttons, links and inputs have `touch-action: manipulation`. The rules pill inside the top bar has no blur of its own (the bar under it is already blurred).
- **The tab icons stay still.** Nick saw them glitch when switching: they shrank and popped back (`navpop`) and the line got thicker on the selected one. Now the icon keeps one line weight selected or not (sidebar too), has no animation, only its colour eases, and each tab sits on its own layer for good (`will-change`) so nothing is re-drawn when the slide starts or stops. Don't animate or re-weight them again.
- **One smoothing pass covers everything else** (the block under "every other movement in the app"): presses on every kind of button dip slightly and ease back; hovers, focus rings and colour changes take .16s; the top bar, page sections, `Info` text, sheets (phone and desktop), the palette, the sync toast, the rules pill's glide, bet bars, the tab underline and the shoe nudge all use the one curve; a switch's knob slides on it. On a computer a soft light drifts after the pointer across the card it is over (`.card::after`, fed `--mx` / `--my` by one `pointermove` listener in `App` that eases a fifth of the way each frame and stops when it has caught up). The sheet's exit is 220 ms because `Sheet` unmounts on a 220 ms timer (change the two together). Chart entrances keep their own kit (`--trace`). All of it is in the `prefers-reduced-motion` rule (`Glider` checks `noMotion()`). Don't add overshoot, a bare `ease`, looping or idle animation.
- **Things that bit**: a backtick inside the `css` template string ends it (the build fails) — no backticks in CSS comments. `backdrop-filter` values are written out, not `var(--…)`, because older Safari ignores a variable in `-webkit-backdrop-filter`. A glass panel inside a wrapper that has its own `backdrop-filter` only sees that wrapper (Chrome), so scrims carry no blur (`.cmdk-wrap`, `.rulesscrim`, `.sheetwrap`). The same happens when the wrapper has an opacity animation that stays applied (`both` / `forwards`): the Jump-to palette showed the page sharp behind it until its scrim was changed to fade by colour (`scrimin`), so fade a scrim by its background colour, never its opacity. The rim's mask is the two-longhand form (`-webkit-mask-composite: xor` and `mask-composite: exclude`). This look could only be checked in Chromium here, not in Safari.
- Tune the variables, not individual elements.
